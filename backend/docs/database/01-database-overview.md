# 01 — Database Overview

## Purpose

This document provides the high-level database architecture for **Praksha Academy SaaS**, a multi-tenant education platform operated by **Prabha Technology**.

---

## Product Context

Praksha Academy is sold as SaaS to multiple education institutes (tenants). Each tenant operates independently:

- Praksha Academy Pune (Tenant A)
- Another Academy (Tenant B)
- Another Education Institute (Tenant C)

All tenants share the same application, but **Tenant A must never access Tenant B's data**.

Additionally, **Prabha Technology** operates a **Master Admin** dashboard to manage the SaaS platform itself — tenants, subscriptions, and platform administration.

---

## Recommended Database

### **MySQL 8.0+** (Recommended)

| Criterion | MySQL 8.0 Assessment |
|---|---|
| SaaS multi-tenancy | Excellent — shared-schema with `tenant_id` is a proven pattern |
| Transactions | Full ACID with InnoDB |
| Relationships | Strong FK support, referential integrity |
| Reporting | Mature query optimizer, window functions, CTEs |
| Scalability | Read replicas, partitioning, connection pooling |
| Indexing | B-tree, composite indexes, covering indexes |
| Data integrity | FK constraints, CHECK constraints (8.0.16+), UNIQUE constraints |
| Python ecosystem | Excellent SQLAlchemy + aiomysql/asyncmy support |
| Production maturity | Widely deployed, managed options (AWS RDS, PlanetScale, etc.) |
| JSON support | Native JSON column type for flexible settings |

### Alternatives Considered

| Database | Why Not Primary |
|---|---|
| PostgreSQL | Equally valid; team plan specifies MySQL/SQL path |
| SQLite | Not suitable for production SaaS |
| MongoDB | Poor fit for relational academic data with strict integrity |

### Engine & Charset

- **Engine:** InnoDB (row-level locking, FK support, crash recovery)
- **Charset:** `utf8mb4` with `utf8mb4_unicode_ci` collation (full Unicode including emoji)

## Multi-Tenancy Strategy

**Shared database, shared schema, tenant-discriminated rows.**

Every tenant-owned table includes a `tenant_id` column referencing `tenants.id`. All queries against tenant data MUST include `WHERE tenant_id = :current_tenant_id`.

Platform-level tables (tenants, subscription_plans, etc.) do not have business `tenant_id` on the table itself — they ARE the platform.

---

## Primary Key Strategy

**UUID (CHAR(36))** for all primary keys.

| Reason | Detail |
|---|---|
| Security | Non-sequential, not guessable |
| Distributed systems | Safe across services and replicas |
| Multi-tenant | No ID collision across tenants |
| API exposure | Safe to expose in URLs without enumeration |
| Merge/migration | No ID conflicts when combining data |

UUIDs are generated by the application layer (Python `uuid.uuid4()`).

---

## Tenant Identification Strategy

**UUID + tenant_code** (recommended)

| Field | Purpose |
|---|---|
| `tenants.id` (UUID) | Internal FK reference, never exposed in URLs |
| `tenants.tenant_code` (VARCHAR) | Human-readable, unique code (e.g., `praksha-pune`) for subdomain/branding |
| `tenants.slug` (VARCHAR) | URL-safe identifier for public-facing tenant pages |

Sequential integer IDs are NOT used as the sole tenant identifier to prevent enumeration attacks.

## Common Column Standards

| Column | Type | Nullable | Purpose |
|---|---|---|---|
| `id` | CHAR(36) | NOT NULL | UUID primary key |
| `tenant_id` | CHAR(36) | Varies | Tenant isolation FK |
| `created_at` | DATETIME(6) | NOT NULL | Record creation timestamp |
| `updated_at` | DATETIME(6) | NOT NULL | Last modification timestamp |
| `deleted_at` | DATETIME(6) | NULL | Soft delete marker |
| `created_by` | CHAR(36) | NULL | User who created the record |
| `updated_by` | CHAR(36) | NULL | User who last updated |
