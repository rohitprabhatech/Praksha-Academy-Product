# 17 — Database Migration Plan

How the database schema moves through environments. **Migrations are not implemented yet** — this documents the planned approach.

---

## Environments

| Environment | Purpose | Database |
|---|---|---|
| Development | Local developer machines | `praksha_academy_dev` |
| Testing | Automated test runs | `praksha_academy_test` |
| Staging | Pre-production validation | `praksha_academy_staging` |
| Production | Live SaaS platform | `praksha_academy_prod` |

Each environment has its own database instance. Never share databases between environments.

---

## Schema Versioning

- **Tool:** Alembic (SQLAlchemy migration framework)
- **Initial migration:** Generated from `database/schema.sql`
- **Version tracking:** `alembic_version` table stores current revision
- **Naming:** `YYYYMMDD_HHMM_description.py` (e.g., `20250901_1200_initial_schema.py`)

---

## Migration Workflow

```
Developer creates/modifies SQLAlchemy model
        ↓
Generate migration: alembic revision --autogenerate -m "description"
        ↓
Review generated migration (never auto-apply blindly)
        ↓
Test migration: alembic upgrade head (on dev)
        ↓
Test rollback: alembic downgrade -1
        ↓
Commit migration file to git
        ↓
CI runs migration on test database
        ↓
Deploy to staging → alembic upgrade head
        ↓
Validate staging
        ↓
Deploy to production → alembic upgrade head
        ↓
Verify production
```

---

## Migration Discipline

### Rules

1. **Never modify a migration that has been applied to staging/production**
2. **Always create a new migration** for schema changes
3. **Review every autogenerated migration** — Alembic can miss edge cases
4. **Test both upgrade and downgrade** before merging
5. **One logical change per migration** (don't bundle unrelated changes)
6. **Include seed data migrations** for roles, permissions, and default plans

### Prohibited

- Running raw `ALTER TABLE` on production without a migration file
- Skipping environments (dev → production directly)
- Using `DROP TABLE` in production without Team Lead approval
- Modifying `alembic_version` manually

---

## Rollback Planning

| Scenario | Action |
|---|---|
| Migration fails mid-apply | Alembic transactions — auto-rollback |
| Migration applied but buggy | `alembic downgrade -1` then fix and re-apply |
| Data migration error | Restore from pre-migration backup |
| Production emergency | Restore from latest backup, then fix migration |

### Pre-Migration Checklist (Production)

- [ ] Migration tested on staging
- [ ] Downgrade tested on staging
- [ ] Backup taken before migration
- [ ] Team Lead approval obtained
- [ ] Maintenance window scheduled (if needed)
- [ ] Rollback plan documented

---

## Initial Schema Deployment

1. Apply `database/schema.sql` as the initial migration
2. Seed platform data:
   - Default roles (master_admin, owner, teacher, student)
   - Default permissions
   - Role-permission mappings
   - Default subscription plans
3. Create initial Master Admin user (via secure script, not in migration)

---

## Production Safety

- Migrations run during low-traffic windows for large changes
- `ALGORITHM=INPLACE, LOCK=NONE` for MySQL online DDL where possible
- Monitor replication lag during migration on read replicas
- Keep migrations idempotent where possible
- Log all migration executions

---

## CI/CD Integration

```
PR opened → CI creates test DB → alembic upgrade head → run tests → drop test DB
Merge to main → deploy staging → alembic upgrade head → smoke tests
Release tag → deploy production → alembic upgrade head → health check
```
